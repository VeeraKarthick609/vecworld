# 04: W4A8, the Q4_K GEMM on the INT8 tensor cores (Task 5b)

**What this is:** the fourth stage of the engine's Q4_K GEMM, and since Task 5b the **default** for the FLUX
painter and the game. Tasks 3 to 5 (`01`..`03`) all compute the same exact product, y = x W^T, with the weight W
decoded from Q4_K and x in bf16 ("W4A16": 4-bit weights, 16-bit activations). This stage also shrinks **x** to 8-bit
integers, one scale per token, so the multiply can run on the GPU's **INT8** tensor cores ("W4A8"). That unit does
4x the bf16 rate on this GPU. The price is accuracy: x loses precision, so the picture changes a little. A
quality gate decides which layers may take that loss.

- `VECWORLD_KERNEL` unset: `w4a8`, with the linears in `config.FLUX_A16_KEEP` on `mma`.
- `VECWORLD_KERNEL=mma`: the lossless W4A16 kernel from Task 5, for every linear.
- `VECWORLD_KERNEL=off`: diffusers. `naive` and `tiled` pick the earlier stages.

## The problem, in plain words

After Task 5 the step took 1.40 s, and about 1 s of it was the GEMMs, running at ~17 TFLOP/s: 91-93% of what cuBLAS
gets in bf16 on this GPU. A better bf16 kernel can't win much more. There are two ways left: do less math (block
caching, Task 8), or do the same math in a cheaper number format. The RTX 3050 Ti's tensor cores multiply 8-bit
integers at 4x the rate they multiply bf16 with an fp32 sum (ledger 1.2: ~76 vs 19.1 TOPS). The weights are
already small integers: a Q4_K code q is 0..15. Only x is in the way.

## W4A16 vs W4A8

```
 W4A16 (Task 5, "mma")                               W4A8 (Task 5b, "w4a8")
 x  bf16  ----------------------\                    x  bf16 --quantize_act--> xq int8, s (per token), xsum
 W  Q4_K --decode to bf16------> bf16 mma, fp32 sum  W  Q4_K --codes q as int8-> int8 mma, int32 sum
                                 (m16n8k16)                                      (m16n8k32 = one sub-block)
                                    |                                               |
                                    v                                               v
                                    y                       rescale in fp32: (d*sc)*sum - (dmin*m)*xsum, then * s
```

## Per-token scales

`quantize_act(x)` (one CUDA kernel) takes each row of x, one token, on its own:

- s_t = max |x_t| / 127, the token's ruler;
- xq = round(x_t / s_t), integers in -127..127 (half to even, as `torch.round`);
- xsum: the sum of xq over each 32 values, for the min term below.

One loud token gets a big s and coarse steps, but only for itself: every other token keeps its own fine ruler.
`test_w4a8_outlier_token` checks exactly that (one token x1000 leaves every other output bit-identical). One scale
for the whole tensor would let the loudest token set the step for all of them.

The cost is rounding: each x value moves by up to s_t / 2. FLUX tokens have a few big values (the study below
measured a token's max |x| at a median 25-50x its median |x|), so most values use only a handful of the 255 levels.
That is the loss the gate has to judge.

## The min-term algebra

Q4_K stores weight i of sub-block j (32 weights) as w_i = (d sc_j) q_i - dmin m_j: d and dmin per 256 weights, the
6-bit sc_j and m_j per 32, the 4-bit code q_i. With x_i = s xq_i, one sub-block's share of an output is

```
 sum_i x_i w_i  =  s * [ (d sc_j) * sum_i xq_i q_i   -   (dmin m_j) * sum_i xq_i ]
                                \__ int32, one mma __/                \__ xsum_j, from quantize_act __/
```

- **sum_i xq_i q_i** is an integer dot product over exactly 32 values: one `mma.sync.m16n8k32.s8.s8.s32`, whose
  k = 32 is one Q4_K sub-block. So one instruction's whole integer sum shares one (d sc_j, dmin m_j) pair, and the
  codes go in as they are (0..15 fits a signed byte). Nothing is decoded.
- **sum_i xq_i** doesn't depend on the weight at all. It is computed once per token and sub-block by
  `quantize_act`, and reused by every output column. That is why the min (offset) term is cheap.
- The kernel accumulates `(d sc_j) * int_sum - (dmin m_j) * xsum_j` in fp32 over the sub-blocks and multiplies by s
  once at the end (the epilogue), then adds the bias and rounds to bf16.

The integer part is exact, so the kernel matches its own definition, a fake-quantized x times the exact gguf weight,
to ~1e-6 (`test_w4a8_gemm_matches_fake_quant`, bar 1e-3). The loss is in x's rounding, not in the kernel.

## How the kernel works

The tiling is Task 5's: 128 x 128 tiles (128 x 64 below 160 tiles), 8 or 4 warps side by side along N, each 128 x
16; K steps of 64 (one 32-byte Q4_K run, two sub-blocks); `cp.async` with zero-fill for ragged edges; 2 stages;
grouped tile order. What changes:

```
 VRAM: xq int8, xsum int32               VRAM: W (Q4_K, unchanged layout)
   | cp.async 16 B (x), 8 B (xsum)         | cp.async 16 B: header + run r
   v                                       v
 shared, 2 stages: A[128][64] int8 (swizzled) | xsum[128][2] | W[BN][48 B] packed
   | ldmatrix.x4                           | two 32-bit loads: words t, 4+t of the run
   v                                       v   & 0x0F0F0F0F (low nibbles: sub-block 2r), >> 4 (high: 2r+1)
 A fragment (s8)                         B fragment (s8) -- no decode, the codes are the integers
                   \                     /
             mma.sync m16n8k32 s8.s8.s32, C = 0x4B400000
                              |
     q = int_as_float(D) - 12582912   (exact int -> float, no conversion instruction)
     acc += (d sc_j) q  ;  acc -= (dmin m_j) xsum_j           (fp32, per sub-block)
                              |
     epilogue: acc * s_token + bias -> bf16
```

- **The fragments, checked against the PTX ISA** ("Matrix Fragments for mma.m16n8k32", .s8):
  - A: lane (g = lane / 4, t = lane % 4) holds rows g and g + 8 at k = 4t..4t+3 and 16 + 4t..16 + 4t+3. A 16 x 32
    int8 tile is 16 rows x 32 bytes, the same shape in bytes as Task 5's 16 x 16 bf16 tile, so the same
    `ldmatrix.x4` addressing hands out exactly that.
  - B: column g at k = 4t..4t+3 and 16 + 4t..16 + 4t+3, which are words t and 4 + t of the 32-byte run. The low
    nibbles of those bytes are sub-block 2r, the high nibbles 2r + 1.
  - C: rows g, g + 8, columns 2t, 2t + 1, as in Task 5. The tests prove all of it: any misplaced fragment would
    miss the 1e-3 bar by orders of magnitude.
- **Swizzle.** An int8 x row is 64 bytes a stage (4 chunks of 16), so chunk c of row r sits at c ^ ((r / 2) % 4):
  `ldmatrix`'s 8 rows then cover all 32 banks.
- **The free int -> float.** The mma's C input is the integer 0x4B400000, the bit pattern of the float 2^23 + 2^22.
  The integer sum (at most 32 x 127 x 15 = 60,960 in size, far below 2^22) lands in the mantissa, and one subtract
  gives the exact float. The hardware int -> float conversion runs at 1/8 of the FMA rate here, and would have
  dominated.
- **Scales per accumulator column.** In Task 5 the scales were applied when decoding B (column g). Here they apply
  to the accumulator (columns 2t, 2t + 1), so each lane unpacks the headers of its own 4 columns per stage.

### What limits it (ablation; ncu still needs root)

The INT8 mma needs about 16 cycles per instruction per SM sub-partition (est., from the 4x rate). Around each one, a lane spends ~12 issue slots
on the rescale alone: subtract, FMA, FMA for 4 outputs. So the kernel is **issue-bound**, not tensor-bound. Timing-only
builds (wrong results), against `mma`:

| Variant | W4A8 / mma, GEMM only |
|---|---|
| **chosen (v1)** | **1.64x** (~27 TFLOP/s bf16-equivalent) |
| no scale unpacking (constant scales) | 1.87x |
| no min-term FMA | 1.92x |
| neither, nor the xsum loads | 2.10x |
| 3 pipeline stages | 1.52x |
| min term as one fp16 `mma.m16n8k8` per super-block (v2, correct) | 1.44x: 18 more registers spill the 128 x 128 tile |

`quantize_act` reads a row once into registers (two-pass for K > 16384): 0.06 ms at 1024 x 3072, 0.35 ms at
1280 x 15360. It runs once per linear call, so q, k and v each quantize the same input (a shared cache is a
possible follow-up).

## Step 1: the study (`scripts/w4a8_study.py`, `bench/t5b-study.json`)

painter ran on `mma` (W4A16). Inside every Q4_K linear, the study also computed in fp32 the output for x
fake-quantized per token, against the output for the exact x, and the pass continued on the mma output. So each
layer's error is its own, not the compounded error of the layers before it. Two contexts: one real 512 image

**What failed, by eye.** Spot 1's score always comes from the same place, columns 516-520: a fog gap between dark
trunks on the left and denser forest on the right. Every walk has it, the lossless ones at 1.08. None of the walks
shows a hard full-height edge there. INT8 activations made that edge slightly crisper, enough to cross 1.1. Attempt 2's
spot 3 (1.14 at column 1795) is a hazy tree beside a sharper one. The walks differ in content, not in kind: a bench
instead of a fenced tree, a different sky, figures in the diffusers walk's spot 3. The lossless diffusers walk differs
from mma's about as much as W4A8's does.

**The result.** Attempt 3 passes, with 70.3% of the token-facing FLOPs on INT8 (206 of 418 linears are kept, but
they hold only 29.7% of the FLOPs), above the brief's floor of half. Its spot 1 margin is thin: 1.098 against the
1.1 limit, where the lossless paths score 1.080-1.082. By eye the sheet looks no worse than Task 5's (the user
judges it at the checkpoint). So `w4a8` with that keep-list is the default (`config.FLUX_KERNEL`, `FLUX_A16_KEEP`).
`VECWORLD_KERNEL=mma` restores the lossless path.

### The step

| | Reference | mma (Task 5) | **w4a8 (Task 5b)** |
|---|---|---|---|
| Step: one 512 window pass (`tile512.s_per_pass_median`) | 2.74 s | 1.40 s | **1.17 s** |
| Achieved TFLOP/s, bf16-equivalent (17.67 TFLOP per pass) | 6.45 | 12.62 | **15.10** |
| % of the measured 19.1 TFLOP/s bf16 peak | 34% | 66.1% | **79.0%** |
| Walk step (`step.s`, `sharp`, 40 window passes) | 61.4 s | 57.4 s | **49.4 s** (1.23 s per window pass) |
| Peak allocated, tile512 / walk step | 1.23 / 1.37 GB | 1.02 / 1.33 GB | 1.02 / 1.33 GB |
| Same-seed 512 image vs mma | - | - | 24.91 dB PSNR (recorded, not gated) |

- **The GEMM.** The token-facing linears do 16.5 TFLOP a pass. At mma's ~16.9 TFLOP/s that is ~0.98 s. With 70.3% on
  INT8 at ~26.6, it is ~0.73 s (est.), and all-INT8 would be ~0.62 s. That is inside the brief's 0.4-0.8 s, at the
  slow end, for two reasons: the kernel is issue-bound at 1.6x rather than 2-4x, and the gate keeps 30% of the
  FLOPs on bf16. The measured step fell 0.23 s, against the estimate's 0.25.
- **The PSNR.** The 512 test image at seed 0 differs from mma's by 24.91 dB: the same sunlit path, ferns and light
  shafts, but several trunks sit elsewhere. Four denoising steps turn the activations' rounding into a slightly
  different sample of the same prompt, not a noisy copy. That is why a lossy stage is judged by the walk gate
  and the eye, not by a match to the reference.
